# 구현 순서와 완료 기준

## 1. 프로젝트 뼈대와 DB

backend 디렉터리에 Java 21/Gradle 기반 Spring Boot를 생성한다. MVC, Validation, Security, JPA, PostgreSQL JDBC, Flyway, Session JDBC, 테스트 의존성을 구성한다. Boot와 문서 생성 라이브러리의 호환 버전을 확정하고 Gradle Wrapper/lock 등으로 재현 가능하게 고정한다.

환경변수는 DB_URL/DB_USERNAME/DB_PASSWORD, UPLOAD_DIR, 신뢰할 프런트 출처 등을 정의하고 실제 암호는 저장소에 넣지 않는다. 개발 DB는 로컬 Docker Compose로 실행할 수 있게 한다. 운영 DB 자동 생성은 Flyway로만 수행한다.

완료 기준: 빈 PostgreSQL에 migration을 적용해 기동되고, 재기동 시 데이터가 유지되며, 상태 확인 API가 DB 장애를 구분한다. H2로 PostgreSQL 통합 테스트를 대체하지 않는다.

## 2. 계정, 세션, 조직

로그인/로그아웃/내 정보/팀 조회를 구현한 후 시스템 관리자 기능을 연결한다. 가상 계정으로 테스트한다. 초기 시스템 관리자는 일회성 bootstrap 절차로 만들고 하드코딩 암호를 배포하지 않는다.

완료 기준: CSRF 누락 요청 거절, 정상 로그인과 세션 ID 교체, 비밀번호 평문 미저장, 권한 회수 반영, 다른 사용자 개인정보 미노출, 비활성 사용자 차단, 만료 후 401을 확인한다.

## 3. 평가룸과 초대

생성/가입/초대/멤버십/운영자 권한/마감을 구현한다. teamIdAtJoin을 가입 시 저장하고 이후 조직 이동으로 바꾸지 않는다. 초대 만료는 요청 시 현재 시간과 비교하며 스케줄러 실행 여부에 의존하지 않는다.

완료 기준: 동시 가입은 멤버십 1개, 동시 초대는 PENDING 1개, 마지막 운영자 제거 불가, 마감 뒤 초대 수락 불가, 타인의 초대 수락 불가.

## 4. 발표와 평가, 결과

순수 평가 제한 정책을 먼저 테스트하고 RatingService에 연결한다. 기존 logic.ts의 대표/발표자 겸임과 팀 스냅샷 규칙을 테스트 사례로 옮긴다. 결과 조회는 SQL/DTO 기반으로 만들고 화면에 주는 점수 범위를 역할별로 분리한다.

완료 기준: 동일 평가 중복 0건, 자기/같은 발표/같은 팀 정책 조합 일치, 미제출 평균 제외, 미제출과 평가 불가 구분, 마감과 동시 제출의 순서 보장. 설정 변경 후 삭제 건수/원점수/집계가 일치해야 한다.

## 5. 첨부와 복합 변경

업로드/다운로드, STAGING/DELETING 정리, 설정 변경 미리보기, 참여자 제거를 구현한다. 파일 스트리밍 중에는 DB 트랜잭션을 오래 유지하지 않는다.

완료 기준: 51 MiB 파일 거절, 11번째 파일 거절, 동시 업로드로 10개 제한 우회 불가, 다른 룸의 첨부 접근 불가, 업로드 도중 프로세스 종료 후 정리, 파일 삭제 실패 재처리, 참여자 제거 중 실패 시 DB 롤백.

## 6. 프런트 연결

1. store.ts의 mockApi/mockUpload/mockDownload를 HTTP client로 대체할 경계를 만든다.
2. 쿠키 인증과 CSRF를 연결하고 sessionStorage 토큰 흐름을 교체한다.
3. `/state` 응답 매퍼로 기존 화면을 연결한다. 날짜 표현, 상태 코드, 개인정보 마스킹을 계약 테스트로 검증한다.
4. 목업 로그인/초기화 UI를 운영 빌드에서 제거한다.
5. 화면별 조회 API로 나누고 전체 상태 재조회와 클라이언트 집계 의존을 줄인다.

브라우저 목업 저장 데이터는 자동 이관하지 않는다. 운영 데이터 이관이 필요하면 입력 정합성과 사용자의 승인 범위를 확인한 별도 import 작업으로 한다.

## 핵심 검증 시나리오

| 시험 | 성공 기준 |
|---|---|
| 50명이 같은 시점에 각자 평가 제출 | 저장 누락/중복 없음, 오류 비율과 p95 측정 |
| 동일 사용자의 중복 제출 | 고유 평가 1개; 수정 허용 정책에 맞는 응답 |
| 마감과 평가 제출 경합 | 먼저 커밋한 작업 기준으로 일관된 상태 |
| 점수 범위 변경과 제출 경합 | 새 범위를 벗어난 평가가 남지 않음 |
| 권한별 결과 조회 | 일반 회원은 자기 점수만, 전체 열람자는 집계, 운영자는 상세 |
| 참여자 제거와 발표 변경 경합 | 대표 없는 발표나 고아 평가 없음 |
| 백엔드 재시작 | DB/파일 유지, 미완료 파일 작업 복구 |
| DB+파일 백업 복원 | 별도 환경에서 결과와 첨부 실제 열람 가능 |

일반 API의 p95 500ms 이내를 초기 목표로 제안하되 파일 전송은 별도로 측정한다. 실제 인스턴스, 데이터량, 조회 빈도를 기록하고 목표 미달 원인이 쿼리/N+1/잠금/메모리인지 먼저 확인한다. 단순 접속 50명과 초당 요청 50개를 같은 부하로 가정하지 않는다.

## 구현 전에 확정할 운영 정책

아래는 문서 작성을 막는 항목이 아니라 해당 기능 개발 때 결정할 사항이다.

- 가입을 공개할지, 사내 이메일 검증/관리자 초대만 허용할지. 권장: 사내 검증 또는 관리자 초대.
- 비밀번호 복구용 메일 전송 수단과 초기 계정 전달 방식.
- 계정 비활성화/평가 데이터/첨부의 보존 기간.
- 첨부 허용 확장자와 악성 파일 검사 수준. 기존 목업은 형식 제한이 없으므로 별도 합의 없이 제한을 바꾸지 않는다.
- 설정 변경 시 기존 평가 삭제라는 목업 정책 유지 여부. 본 설계는 유지하되 영향 미리보기와 작업 기록을 추가한다.
- 09~18시 이용 제한이 업무 규칙인지 단순 비용 절감 목적의 인프라 운영시간인지.

AWS 배포와 시작·중지 스케줄 작업은 이 구현 설계 범위에서 보류한다. 후속 배포 때 자동 기동, HTTPS, DB/파일 백업, 복원 시험과 DB 포트 비공개를 준비한다.
