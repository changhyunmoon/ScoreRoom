# Spring API·인증·캐시 연결

백엔드 [API 설계](../backend/04-api-and-security.md)를 기준으로 한다. 아래 조회 계약 중 추가 제안은 백엔드 구현 시 함께 반영한다. 현재 프런트엔드는 아직 목업 API만 호출한다.

## HTTP 클라이언트

shared/api/client.ts가 `/api/v1` 접두어, 쿠키, JSON 처리, AbortSignal, 오류 변환을 맡는다. fetch를 기본으로 하며 Axios를 필수로 추가하지 않는다. FormData 업로드는 브라우저가 boundary를 지정하도록 Content-Type을 직접 설정하지 않는다. 204 응답에 JSON 파싱을 시도하지 않는다.

ApiError는 status/code/message/fieldErrors/requestId를 가진다. 예기치 않은 HTML/빈 오류 응답도 안전한 공통 오류로 변환한다. URL 인코딩, 요청 취소, 네트워크 오류를 구분한다. `VITE_*` 환경변수는 브라우저에 공개되므로 비밀값을 넣지 않는다.

## 세션과 CSRF

1. 앱 시작 시 `/auth/csrf`, `/me`를 조회한다. 미인증 401은 정상 익명 상태로 해석한다.
2. 쓰기 요청은 서버가 알려준 CSRF 헤더 이름/값과 세션 쿠키를 포함한다.
3. 로그인/로그아웃 성공 후 CSRF를 다시 받아 토큰 교체를 반영한다.
4. `/me`의 확인된 사용자로 캐시 영역을 분리한다. 사용자 전환과 로그아웃 시 진행 중 조회를 취소하고 기존 사용자 캐시/폼을 제거한다.
5. 보호 API 401은 한 번만 인증 만료 처리하고 로그인으로 이동한다. 403은 권한 부족일 수 있으므로 세션을 자동 제거하지 않는다.

단일 출처 운영을 기본으로 한다. 개발은 Vite의 `/api` proxy로 Spring에 연결해 같은 방식을 사용한다. API 서버에 직접 다른 출처로 연결한다면 credentials 포함, CORS 허용 출처/자격 증명, 쿠키 속성을 함께 조정해야 한다.

CSRF 오류를 일반 403과 구분하는 서버 오류 코드를 계약한다. 토큰을 새로 받은 뒤 재제출을 안내한다. 변경 요청을 무조건 자동 재전송하지 않는다. 로그아웃 서버 요청 실패 시 로컬 화면만 지우고 서버 세션도 종료됐다고 표시하지 않는다. 실패를 알리고 재시도할 수 있게 한다.

## 서버 캐시와 갱신

TanStack Query 도입 시 query key에는 로그인 사용자와 조회 조건을 포함한다. 아래는 개념 예시다. 실제 API/훅 이름은 구현 시 확정한다.

| 데이터 | query key 예시 | 주 사용 화면 |
|---|---|---|
| 인증 사용자 | ['session','me'] | 앱 초기화/공통 헤더 |
| 룸 목록 | ['user',uid,'projects',{search,page,sort}] | 메인 |
| 룸 정보/권한 | ['user',uid,'project',pid] | 룸 공통 레이아웃 |
| 발표 목록 | ['user',uid,'project',pid,'presentations',{page,sort,filter}] | 평가 |
| 내 평가 | ['user',uid,'project',pid,'ratings','me'] | 평가 |
| 집계 | ['user',uid,'project',pid,'results','summary'] | 결과/운영 |
| 개별 평가 상세 | ['user',uid,'project',pid,'results','detail'] | 운영자 상세 |
| 초대 | ['user',uid,'invitations'] | 헤더 알림 |

캐시 key가 보안 장치는 아니다. 서버가 매번 접근 권한을 검사한다. 권한 변경이 확인되면 해당 결과 상세 캐시를 제거하고 현재 권한으로 다시 조회한다. 캐시를 localStorage 등에 영속화하지 않는다.

조회는 서버 오류/일시적 네트워크 실패에만 제한적으로 재시도하고 400/401/403/404는 자동 재시도하지 않는다. 쓰기 요청의 retry는 기본 비활성이다. 쿼리 취소 신호를 fetch에 전달하고 같은 query key를 사용하는 컴포넌트의 중복 요청을 줄인다.

열린 OPEN 룸과 초대 알림은 초기 제안으로 15초 간격으로 갱신한다. 숨겨진 탭·오프라인에서는 중단하고 복귀 시 재조회한다. 마감 룸은 주기 갱신을 중단한다. 결과 상세는 실제 패널이 열렸을 때 조회한다. 동접 50명에서 모든 사용자가 매번 전체 DB를 내려받지 않도록 요청량을 측정한다. 폴링은 서버 캐시만 바꾸고 dirty 폼을 초기화하지 않는다.

| 변경 | 성공 후 무효화할 데이터 |
|---|---|
| 평가 저장 | 내 평가, 발표 진행도, 룸 집계 |
| 발표 변경/순서 | 발표 목록/상세, 집계 |
| 초대 수락/거절 | 초대, 룸 목록, 해당 룸 참여 정보 |
| 설정 변경/마감 | 해당 룸의 정보/권한/발표/내 평가/결과 전체 |
| 참여자 제거/운영자 변경 | 해당 룸 관련 캐시, 본인 접근 권한 |
| 프로필/팀 변경 | me, 조직도; 가입 당시 소속 스냅샷은 바꾸지 않음 |

파괴적 작업이나 점수 저장에는 우선 낙관적 업데이트를 적용하지 않는다. 성공 알림은 서버 커밋 확인 후 표시하고 조회 실패를 저장 실패와 구분한다.

## DTO와 백엔드 보완 계약

기존 프런트의 DB 타입을 PostgreSQL 테이블 구조 그대로 옮기지 않는다. 화면 DTO에는 displayName, 역할, 평가 가능 사유, 요약 등 필요한 표현을 서버에서 조립한다. 기존 rank와 SQL sort_order 등 이름 차이는 어댑터에서 명시적으로 변환한다. 시간은 백엔드 제안에 따라 epoch milliseconds, ID는 문자열, 없는 평균은 null이다.

현재 사용자의 권한은 canRate/canEditPresentation/canManageRoom/canViewResults/canViewRatingDetails 같은 capability 응답으로 명확히 하길 제안한다. 제출 시점의 최종 권한은 서버가 재검사한다. 목록이 페이지 단위가 되면 목록 배열만으로 전체 진행도/결과를 계산하지 않는다.

백엔드에 함께 추가할 조회: `/projects/{pid}/presentations/{id}` 상세, 페이지 응답의 items/page/size/total, 룸 capability, 운영자용 평가 상세, 룸 참여자 목록과 초대 대상 검색. 현재 백엔드 경로 표에 없는 항목은 구현 시 OpenAPI에 먼저 합의한다. 조직도 사용자 선택에는 공개용 최소 프로필을 사용하고 일반 회원에게 이메일/전화번호를 전달하지 않는다.

## 파일 전송

첨부 제한은 파일당 50 MiB, 발표당 10개다. 클라이언트에서 먼저 검사하고 서버 제한을 우회 가능하다고 전제한다. 기본 fetch 업로드는 전송 중 상태를 표시하며 실제 바이트 진행률이 필요할 때 별도 전송 수단을 검토한다. 파일을 base64로 변환해 store에 넣지 않는다.

다운로드는 인증 요청으로 받은 Blob과 안전한 파일명을 사용하고 Object URL을 사용 후 해제한다. 응답 오류를 파일로 저장하지 않는다. 로컬 미리보기 URL도 파일 제거/화면 종료 시 해제한다.

## 목업 전환

첫 단계에서는 api 어댑터만 바꾸고 `/state`로 현재 화면을 연결한다. 다음 단계에서 화면 하나씩 Query 훅으로 전환한다. mock은 개발/테스트 전용 진입점에서만 가져오고 운영 진입점이 실제 직원 정보가 포함된 시드나 초기화 API를 import하지 않게 한다. 사용자별 브라우저 데이터는 자동 이관하지 않는다.
